# ConsensusSeam v0.1 设计说明

## 研究问题

ConsensusSeam v0.1 研究多 Agent 是否能够阅读 Go 共识实现源码，识别七类基础测试控制能力，并通过小规模修改补充缺失接口。

框架的评价重点是：

- 能否找到真实代码边界；
- 能否区分已有能力、可补充能力和侵入式能力；
- 是否复用目标项目已有接口和测试设施；
- 修改是否低侵入；
- 原有功能和测试是否保持；
- 最终使用者能否根据报告调用这些接口。

它不是测试策略系统，也不对任意目标作完备正确性承诺。

## 七项能力与六种状态

v0.1 固定分析消息捕获、消息注入、时间控制、随机性控制、生命周期控制、状态观察和外部输入七项能力。

六种能力状态保持不变：

- `SUPPORTED`：目标已经完整提供；
- `PATCHABLE`：可以低侵入补充；
- `PARTIAL`：已有部分能力；
- `INVASIVE`：需要修改核心语义或发明目标未定义的行为；
- `UNKNOWN`：证据不足；
- `NOT_APPLICABLE`：相对于当前系统边界不适用。

这些状态是实验结果，不应为了简化工作流而压缩。特别是 `INVASIVE` 与 `UNKNOWN`、`PARTIAL` 与 `SUPPORTED` 分别表达不同研究信息。

## 通用语义与目标实现分离

全局规范统一测试方看到的核心对象、动作名称和语义，但不规定目标内部结构。

例如，消息注入要求“把选中的已捕获消息交给记录目标的正常协议入口”，但不假定目标一定拥有：

- 特定传输接口；
- 全局节点注册表；
- 固定的内部传输或节点注册实现；
- 同步错误返回；
- 统一的生产模式和测试模式切换方式。

Agent 应使用目标项目最自然的形态实现接口。某个目标采用的包装、测试环境、节点类型或消息入口不得回写为全局前提。

“最自然”还要从声明测试方的可达范围判断。项目自用测试包可以帮助 Agent
理解正确调用方式并承载回归验证，但不能仅因为容易修改就成为默认或唯一
交付面。优先复用真实公开协议入口，并在其上增加独立、低侵入的测试支持；
只有现有测试包本身是明确的外部 API，或确实是侵入最低的完整方案时，才将
其作为主要接口。该偏好不能反过来迫使 Agent 把测试机制写入协议核心。

## 底层原语与测试支持改造

能力分析必须区分两个层次：

1. 底层原语：协议已经提供的输入、输出、Tick、状态读取、构造或恢复方法；
2. 测试接口：测试人员可以直接调用、保存和组合这些原语的稳定接口。

底层原语是实现缓存控制面的依据，但不能自动得到 `SUPPORTED`。例如：

- 一次性消息批次、channel 或发送 hook 是消息输出原语；
- 正常协议处理函数是消息输入原语；
- 测试可见缓存、指定实例操作和正常输入入口的明确组合才构成完整消息控制能力。

“测试方可以自行把输出复制到新切片”只能说明它能够基于原语另写测试设施，不能说明被分析目标已经提供缓存。完整缓存必须在投递前接管受控输出，并通过统一的 `MessageController` 提供 `Pending`、`Drop`、`Clear` 和 `Inject`。测试方检查 `PendingMessage` 内容后使用稳定的不透明 `MessageHandle` 操作实例；Handle 失效后不能静默改指。

受控模式下捕获点还必须独占继续传递权，不能另起消费者与协议消费者竞争。`Inject` 由 Controller 定位实例、校验真实目标并调用同一路径的正常输入入口；确认输入接受后才移除消息。请求和响应分别缓存，response channel 或 future 仍作为原交换的完成机制。v0.1 不把消息所有权交给测试方，也不提供 `Take`、消息修改、重定向或复制。

Go 结构体按值复制不能自动证明快照安全，必须继续检查嵌套 slice、map、pointer、interface、channel、future 和可消费流。随机性控制要求相同初始状态、控制参数和测试调度重现每个实例相同的选择序列，并让测试方知道实际选择值；值可以随决策变化。共享 seeded 随机源只要在相同调度下稳定分配选择即可，不强制每实例随机源或固定常量。

Analyzer 对每项能力都应回答：

- 现有原语是什么；
- 是否已经能直接供测试使用；
- 现有测试接口是否完整；
- 还缺少哪些测试支持；
- 可以采用包装、hook、依赖注入、配置项、只读 accessor 或测试 harness 扩展中的哪些方式；
- 建议改造是否越过低侵入边界。

如果仍需新增测试支持并且可以低侵入完成，状态应为 `PATCHABLE`，不能因为底层原语已经存在就标为 `SUPPORTED`。如果现有公开测试接口已经完整满足合同，则不应为了形式统一重复修改。

这条判断需要按能力合同解释，不能把消息缓存的显式包装要求推广到所有能力。生命周期分别要求同实例 Pause/Resume、正常 Stop、突然 Crash 和正常 Restart。Agent 可以加入默认关闭且不改变语义的窄核心 hook；如果某项操作必须改变协议或持久化语义，则保持统一方法形状并返回 `ErrLifecycleUnsupported`。Seam 保持原持久化与发送顺序，并把恢复后的追赶留给协议和测试场景。

## 多实现路径发现

共识库可能同时提供同步、异步、嵌入式和完整节点等多种路径。人工通常只知道仓库和系统边界，不应被要求提前列出这些内部路径。

大型或多子系统仓库可以由人工指定可选的文件夹级权限：`scope_roots` 可分析和
修改，`evidence_roots` 只读；省略时分别默认为仓库根目录和空。它们只约束源码
访问，不要求人工定位具体文件。能力范围仍由 `system_boundary` 声明的协议平面
决定；共享 P2P、Service、存储或顶层容器即使可见，也不会自动进入转换范围。
控制对象可以是节点、Reactor、Service、Actor、组件或进程，不预设具体架构。

Analyzer 应从源码、公开接口和已有测试设施中发现所有实质不同的端到端路径。路径表示一组一致的公开输出边界、缓存或目标所有权、输入边界和控制方式。这里的“实质不同”是指至少一项不同：

- 协议输入入口；
- 协议输出或消息发送边界；
- 时间、随机性或生命周期控制入口；
- 同步/异步完成语义；
- 公开受控对象类型或测试运行时。

消息类型、timer 位置、随机调用点、helper、文件、同一运行对象上的多个 accessor、到达同一控制面的内部条件分支，以及一条传递路线中连续的发送/接收边界不构成新路径；共享 transport、缓存、输入、所有权和完成模型的不同消息 handler 仍是一条路径。路径必须从声明测试方能够构造或调用的公开控制面开始。只有所有权、输入输出边界或完成语义变化时才拆分。排除项、拒绝状态和相邻原语进入证据或限制，不能作为路径；能力为 `PATCHABLE`、`PARTIAL` 或 `INVASIVE` 时也要保留适用路径。

Analyzer 应通过 `execution_paths`、`boundary`、`entrypoints` 和 `limitations` 记录发现结果。`entrypoints` 只列未修改源码中已存在、且声明测试方可调用的接口；内部调用点属于证据，候选 API 只进入 `suggested_changes`。全局规范不预设一个目标有多少条路径，也不预设路径类型。能力总状态应综合所有已发现路径：全部已有时是 `SUPPORTED`；只要至少一条当前缺失路径能够低侵入补充，就可以是 `PATCHABLE`，同时明确其他不可补充路径；已有部分路径、但剩余缺口都无法在 v0.1 安全补充时是 `PARTIAL`。`SUPPORTED` 的限制不能反过来否定其正向路径、入口或快照安全声明。对于消息能力，一条完整缓存路径不能替代另一条只有输出或输入原语的路径。

低侵入按语义而不是文件数量判断。对真实时间系统，即使 Clock/Timer 注入需要机械修改多个文件，只要生产默认、timer 顺序和协议状态转换条件保持不变，仍可判为 `PATCHABLE`。如果实现必须协调独立生命周期、持久化、应用或进程所有权，即使每处修改很小也属于侵入式。

Transformer 必须覆盖所有已发现且能够通过缓存、薄包装、hook 或依赖注入低侵入实现的路径，并在 `covered_paths` 中逐条列出。当前缺少缓存或 wrapper 正是待实现缺口，不能作为只做最容易或项目自用测试路径的理由。确实需要改变协议语义的路径才进入 `uncovered_paths` 和 `notes`。消息捕获和注入虽然保留两个报告字段，但必须使用同一组路径名称逐条形成缓存到输入的闭环；A 路径的捕获不能与 B 路径的注入合并成完整支持。两者同时被选择时仍使用一次联合 Transformer 调用。

Transformer 应参考 Analyzer 的 `suggested_changes`，但不被某一种实现手段绑定。它可以组合多种允许方式，只要实际改造保持低侵入并在 interface report 的 `implementation_approach` 中如实记录。

若某条已发现路径需要越过当前系统边界，应记录为未覆盖，而不是要求人工事先排除它，也不能用另一条容易实现的路径代替它。

## 固定工作流

### Agent 1：能力分析

Agent 1 只读目标源码，对七项能力给出状态、证据、边界、入口和限制。它不能从函数名或协议简介推断行为，也不能把目标 ID 自动等同于目标对象绑定。

### Agent 2：低侵入实现

Agent 2 只处理本次实验选中的 `PATCHABLE` 能力。优先顺序是：

1. 复用声明测试方已经能够调用的公开接口；
2. 围绕公开协议路径添加或扩展小型测试支持层；
3. 添加薄包装、配置 hook 或只读访问器；
4. 在不改变核心协议语义的前提下注入依赖；
5. 如果不能安全实现，报告 `INVASIVE_REDISCOVERED`。

目标已有的项目自用测试包可以作为参考与验证位置；只有它被明确提供给外部
测试方，或是低侵入完成合同的最佳位置时，才优先扩展。对外部测试方声明的
`public_entrypoints` 不能依赖同包权限、`_test.go` 符号或私有测试 runner。

Agent 2 只生成验证新增行为所需的最少 Go 测试和使用说明，不能修改已有测试来降低通过难度，也不扩写重复覆盖或大规模参数组合。

### Agent 3：独立审查

Agent 3 不修改代码，检查：

- 修改是否与能力报告一致；
- 是否越过低侵入边界；
- 是否保留原协议逻辑和原测试；
- 新接口是否在声明范围内可调用；
- 使用说明是否反映真实入口和限制。

Reviewer 不承担完整协议安全证明。

### Controller：确定性执行

Controller 负责：

- 强类型 Agent 输入输出；
- 有界重试和固定失败路由；
- 每轮全新 Git worktree；
- baseline、构建和原测试；
- 项目 manifest 配置的基础能力检查；
- 产物、补丁规模和模型成本审计。

## 完整生成与自动修订流程

开放式接口生成无法在实验前预知最终 Go API，因此不强制预写能够直接调用未知符号的隐藏测试。`patch` 是一个可以独立结束的完整主流程：

1. `patch` 发现并生成目标原生接口；
2. Controller 按 `PATCHABLE` 能力分别调用 Transformer，并在同一候选 worktree 中累积修改；
3. 候选通过格式化、构建和独立 Reviewer；
4. 系统输出 `changes.patch`、包含完整代码的候选 worktree、`interface-report.json` 和 `USAGE.md`。

到这里接口生成已经完成。使用者可以直接审阅、测试或集成候选代码。

Agent 3 是首次生成流程的主要自动质量反馈入口。它必须把问题分成：

- 能力分类或低侵入边界错误：`REVISE_AGENT1`；
- 实现、接口声明或路径覆盖错误：`REVISE_AGENT2`；
- 源码证据无法裁决：`NEEDS_HUMAN`；
- 不影响能力合同成立的剩余限制：`risks`。

前三类不能隐藏在 `PASS.risks` 中。Agent 2 修订时，Controller 在新的隔离 worktree 中重新应用上一版候选，再根据 Reviewer 证据继续修改；这样既避免失败工作区残留，也不要求 Agent 从空白重新生成。

审查规则保持目标无关：检查入口对声明的使用者是否可达、返回数据是否泄漏可变内部引用、新旧状态是否有统一一致性来源、成功与消费是否对应真实输入边界、配置值是否遵守目标合法域。具体目标无法低侵入满足时应缩小覆盖声明，而不是把目标特例写进全局 Prompt。

## 验证边界与 run 的定位

`run` 不是未知目标生成接口的必经步骤。它是一种预配置评测/回归模式，适用于接口契约和 capability checks 已经稳定的目标，例如 Mini Raft 的重复实验。它从目标原提交重新开始，执行 Analyzer、Transformer、Reviewer，并使用 manifest 中已有的 checks 自动验证和反馈修复。

v0.1 按使用场景提供两种验证强度：

1. `patch`：格式化、候选构建和独立 Reviewer；
2. `run`：额外执行原始目标 baseline、候选原测试和预配置能力检查。

未知目标没有预配置 checks 时使用 `patch`，不应为了调用 `run` 而预先猜测 Agent 将生成的 API。一个成熟目标可以增加更严格的回归检查，但额外检查只属于该目标，不自动成为其他目标的强制要求。

隐藏 fixture 和人工 ground truth 属于正式评测工具：

- fixture 在 Reviewer 完成后才进入候选 worktree；
- ground truth 只做事后评分；
- 二者都不会进入 Agent Prompt。

因此，工程使用不要求先人工写出一份完整答案。

## 实验失败的处理规则

每次失败先分类，再决定是否修改框架。

### 通用框架错误

例如 Agent 能看到隐藏 fixture、worktree 污染原仓库、结构化输出无法审计。这类问题修改 ConsensusSeam。

### 目标项目限制

例如某个目标只有异步投递、某种运行模式没有同步错误、某个测试辅助包只支持连续节点 ID。这类问题记录在该目标报告或 evaluation 中。

### v0.1 范围之外

例如真实网络调度、跨进程持久化恢复、所有并发竞争和完整协议证明。明确记录后停止扩张，不新增全局规则。

单次实验失败是研究数据，不等于框架必须修到该实验通过。

## 已保留的工程安全措施

- Python 3.10+，不依赖 3.12 专属功能；
- Pydantic 严格 Schema；
- Agent 角色工具隔离；
- Git worktree 隔离；
- 禁止修改已有 Go 测试；
- 失败候选不会污染下一轮；
- 模型推理正文不进入审计产物；
- API 密钥不写入日志；
- 目标和控制器版本写入 `run-config.json`。

这些措施解决的是实验隔离和可追溯性，不应继续扩展成目标语义的完备 gate。

## 当前阶段

Mini Raft 用于验证小型完整工作流；etcd/raft 用于检查显式逻辑时间和多种公开
运行路径；HashiCorp Raft 用于检查异步运行、真实时间和 Transport 包装。

接下来的首要任务是：

1. 保持 Agent 1 六种分类和 Agent 2 单一角色稳定；
2. 固定测试方使用的 Controller、Handle 和核心动作名称，同时不强制目标内部路径数量、节点结构或实现技术；
3. 通过 `USAGE.md` 接口矩阵与示例服务测试方，通过 `AUDIT.md` 保存完整英文技术分析；
4. 将额外严格检查留在具体 evaluation，并用不同结构的共识实现继续验证通用性。
