# ConsensusSeam v0.1 设计说明

## 研究问题

ConsensusSeam v0.1 研究多 Agent 是否能够阅读 Go 共识实现源码，识别七类基础测试控制能力，并通过小规模修改补充缺失接口。

框架的评价重点是：

- 能否找到真实代码边界；
- 能否区分已有能力、可补充能力和侵入式能力；
- 是否复用目标项目已有接口和测试设施；
- 修改是否低侵入；
- 原有功能和测试是否保持；
- 最终使用者能否根据报告调用这些接口。

它不是测试策略系统，也不对任意目标作完备正确性承诺。

## 七项能力与六种状态

v0.1 固定分析消息捕获、消息注入、时间控制、随机性控制、生命周期控制、状态观察和外部输入七项能力。

六种能力状态保持不变：

- `SUPPORTED`：目标已经完整提供；
- `PATCHABLE`：可以低侵入补充；
- `PARTIAL`：已有部分能力；
- `INVASIVE`：需要修改核心语义或发明目标未定义的行为；
- `UNKNOWN`：证据不足；
- `NOT_APPLICABLE`：相对于当前系统边界不适用。

这些状态是实验结果，不应为了简化工作流而压缩。特别是 `INVASIVE` 与 `UNKNOWN`、`PARTIAL` 与 `SUPPORTED` 分别表达不同研究信息。

## 通用语义与目标实现分离

全局规范只描述能力语义，不规定统一 Go API。

例如，消息注入要求“把选中的已捕获消息交给记录目标的正常协议入口”，但不假定目标一定拥有：

- 特定传输接口；
- 全局节点注册表；
- 固定名称的 `NewMessageController`；
- 同步错误返回；
- 统一的生产模式和测试模式切换方式。

Agent 应使用目标项目最自然的形态实现接口。某个目标采用的包装、测试环境、节点类型或消息入口不得回写为全局前提。

## 底层原语与测试支持改造

能力分析必须区分两个层次：

1. 底层原语：协议已经提供的输入、输出、Tick、状态读取、构造或恢复方法；
2. 测试接口：测试人员可以直接调用、保存和组合这些原语的稳定接口。

底层原语是实现缓存控制面的依据，但不能自动得到 `SUPPORTED`。例如：

- 一次性消息批次、channel 或发送 hook 是消息输出原语；
- 正常协议处理函数是消息输入原语；
- 测试可见缓存、指定实例操作和正常输入入口的明确组合才构成完整消息控制能力。

“测试方可以自行把输出复制到新切片”只能说明它能够基于原语另写测试设施，不能说明被分析目标已经提供缓存。完整缓存必须在投递前接管受控输出，并提供枚举、`Take`、`Drop` 和 `Clear`。`Take` 移除并返回消息，属于捕获缓存操作。测试方根据消息内容选择实例；引用要么仍命中观察到的实例，要么报告过期，不能静默改指。目标原生记录、opaque handle、token、指针或 mutation-safe index 都可以使用，不要求永久数字 ID。

受控模式下捕获点还必须独占继续传递权，不能另起消费者与协议消费者竞争。注入允许两种形式：分离式 `Take + ProtocolInput` 由已经持有节点关系的测试方完成正常输入；组合式单调用由 facade 定位实例、绑定目标并完成输入。单调用不表示事务原子性。两种形式都必须说明成功、失败和未确认异步投递的缓存效果。捕获的请求必须进入正常请求处理入口，完成响应不能替代请求注入；response channel 或 future 仍作为原交换的完成机制。

Go 结构体按值复制不能自动证明快照安全，必须继续检查嵌套 slice、map、pointer、interface、channel、future 和可消费流。随机性控制也不只要求全局随机序列可重放：声明范围内的同一实例必须获得相同选择，并发调用顺序可能改变随机值归属时仍是缺口。

Analyzer 对每项能力都应回答：

- 现有原语是什么；
- 是否已经能直接供测试使用；
- 现有测试接口是否完整；
- 还缺少哪些测试支持；
- 可以采用包装、hook、依赖注入、配置项、只读 accessor 或测试 harness 扩展中的哪些方式；
- 建议改造是否越过低侵入边界。

如果仍需新增测试支持并且可以低侵入完成，状态应为 `PATCHABLE`，不能因为底层原语已经存在就标为 `SUPPORTED`。如果现有公开测试接口已经完整满足合同，则不应为了形式统一重复修改。

这条判断需要按能力合同解释，不能把消息缓存的显式包装要求推广到所有能力。例如生命周期第一版允许调用方停止/恢复调度，或组合目标已有构造与状态所有权完成重建；缺少单独的 harness 命令只是易用性差异，不自动构成功能缺口。网络断连或分区时节点仍执行本地协议行为，不能单独算作生命周期停止。

## 多实现路径发现

共识库可能同时提供同步、异步、嵌入式和完整节点等多种路径。人工通常只知道仓库和系统边界，不应被要求提前列出这些内部路径。

Analyzer 应从源码、公开接口和已有测试设施中发现所有实质不同的端到端路径。路径表示一组一致的公开输出边界、缓存或目标所有权、输入边界和控制方式。这里的“实质不同”是指至少一项不同：

- 协议输入入口；
- 协议输出或消息发送边界；
- 时间、随机性或生命周期控制入口；
- 同步/异步完成语义；
- 公开节点类型或测试运行时。

消息类型、helper、文件、同一运行对象上的多个 accessor、到达同一控制面的内部条件分支，以及一条传递路线中连续的发送/接收边界不构成新路径；只有所有权、输入输出边界或完成语义变化时才拆分路径。排除项、拒绝状态和相邻原语进入证据或限制，不能作为路径。

Analyzer 应通过 `execution_paths`、`boundary`、`entrypoints` 和 `limitations` 记录发现结果。`entrypoints` 只列声明测试方可调用的接口，内部调用点属于证据。全局规范不预设一个目标有多少条路径，也不预设路径类型。能力总状态应综合所有已发现路径：全部已有时是 `SUPPORTED`；只要至少一条当前缺失路径能够低侵入补充，就可以是 `PATCHABLE`，同时明确其他不可补充路径；已有部分路径、但剩余缺口都无法在 v0.1 安全补充时是 `PARTIAL`。`SUPPORTED` 的限制不能反过来否定其正向路径、入口或快照安全声明。对于消息能力，一条完整缓存路径不能替代另一条只有输出或输入原语的路径。

Transformer 应尝试覆盖所有已发现且能够低侵入实现的路径，并在 `covered_paths` 中列出已覆盖路径。不能安全实现的路径写入 `uncovered_paths` 和 `notes`，不能为了让报告看起来完整而修改协议核心，也不能静默只实现最容易的一条路径。消息捕获和注入虽然保留两个报告字段，但必须使用同一组路径名称逐条形成缓存到输入的闭环；A 路径的捕获不能与 B 路径的注入合并成完整支持。两者同时被选择时仍使用一次联合 Transformer 调用。

Transformer 应参考 Analyzer 的 `suggested_changes`，但不被某一种实现手段绑定。它可以组合多种允许方式，只要实际改造保持低侵入并在 interface report 的 `implementation_approach` 中如实记录。

若某条已发现路径需要越过当前系统边界，应记录为未覆盖，而不是要求人工事先排除它，也不能用另一条容易实现的路径代替它。

## 固定工作流

### Agent 1：能力分析

Agent 1 只读目标源码，对七项能力给出状态、证据、边界、入口和限制。它不能从函数名或协议简介推断行为，也不能把目标 ID 自动等同于目标对象绑定。

### Agent 2：低侵入实现

Agent 2 只处理本次实验选中的 `PATCHABLE` 能力。优先顺序是：

1. 复用目标已有测试接口；
2. 扩展目标已有测试辅助包；
3. 添加薄包装或只读访问器；
4. 在不改变核心协议语义的前提下注入依赖；
5. 如果不能安全实现，报告 `INVASIVE_REDISCOVERED`。

Agent 2 只生成验证新增行为所需的最少 Go 测试和使用说明，不能修改已有测试来降低通过难度，也不扩写重复覆盖或大规模参数组合。

### Agent 3：独立审查

Agent 3 不修改代码，检查：

- 修改是否与能力报告一致；
- 是否越过低侵入边界；
- 是否保留原协议逻辑和原测试；
- 新接口是否在声明范围内可调用；
- 使用说明是否反映真实入口和限制。

Reviewer 不承担完整协议安全证明。

### Controller：确定性执行

Controller 负责：

- 强类型 Agent 输入输出；
- 有界重试和固定失败路由；
- 每轮全新 Git worktree；
- baseline、构建和原测试；
- 项目 manifest 配置的基础能力检查；
- 产物、补丁规模和模型成本审计。

## 完整生成流程与可选 repair

开放式接口生成无法在实验前预知最终 Go API，因此不强制预写能够直接调用未知符号的隐藏测试。`patch` 是一个可以独立结束的完整主流程：

1. `patch` 发现并生成目标原生接口；
2. Controller 按 `PATCHABLE` 能力分别调用 Transformer，并在同一候选 worktree 中累积修改；
3. 候选通过格式化、构建和独立 Reviewer；
4. 系统输出 `changes.patch`、包含完整代码的候选 worktree、`interface-report.json` 和 `USAGE.md`。

到这里接口生成已经完成。使用者可以直接审阅、测试或集成候选代码，是否执行 `repair` 不影响主流程产物的生成。

Agent 3 是首次生成流程的主要自动质量反馈入口。它必须把问题分成：

- 能力分类或低侵入边界错误：`REVISE_AGENT1`；
- 实现、接口声明或路径覆盖错误：`REVISE_AGENT2`；
- 源码证据无法裁决：`NEEDS_HUMAN`；
- 不影响能力合同成立的剩余限制：`risks`。

前三类不能隐藏在 `PASS.risks` 中。Agent 2 修订时，Controller 在新的隔离 worktree 中重新应用上一版候选，再根据 Reviewer 证据继续修改；这样既避免失败工作区残留，也不要求 Agent 从空白重新生成。

审查规则保持目标无关：检查入口对声明的使用者是否可达、返回数据是否泄漏可变内部引用、新旧状态是否有统一一致性来源、成功与消费是否对应真实输入边界、配置值是否遵守目标合法域。具体目标无法低侵入满足时应缩小覆盖声明，而不是把目标特例写进全局 Prompt。

`repair` 只是一条可选的质量增强路径：

1. 使用者根据实际 `interface-report.json` 和 `USAGE.md` 编写后置测试；
2. `repair` 在原目标提交上重新应用候选补丁，执行后置测试；
3. 测试失败时只把结构化命令结果反馈给 Agent 2；
4. 每轮修订仍经过已有测试保护、格式化、构建、独立 Reviewer 和后置测试。

`repair` 不重新运行 Analyzer，也不把 evaluator-only fixture 暴露给 Agent。它读取原实验的：

- `capability-report.json`；
- `interface-report.json`；
- `changes.patch`；
- `run-config.json`。

原目标提交必须与当前目标仓库 `HEAD` 一致。每轮 repair 都从该 clean revision 创建 fresh worktree，再应用上一轮候选 patch，避免失败工作区残留，同时保留 Agent 2 的连续修复能力。

如果后置测试第一次就通过，说明接口已被实际使用验证；如果经过 Agent 2 修复后通过，工作流返回 `REPAIRED`。这两种结果都只覆盖实际测试场景，不声称完备协议正确性。

后置 checks 是生成后的测试输入，不是生成前 ground truth。它们一旦进入某次 repair 运行，就作为该运行的稳定测试目标，Agent 2 不能通过修改已有测试来规避失败。

## 验证边界与 run 的定位

`run` 不是未知目标生成接口的必经步骤。它是一种预配置评测/回归模式，适用于接口契约和 capability checks 已经稳定的目标，例如 Mini Raft 的重复实验。它从目标原提交重新开始，执行 Analyzer、Transformer、Reviewer，并使用 manifest 中已有的 checks 自动验证和反馈修复。

v0.1 按使用场景提供三种验证强度：

1. `patch`：格式化、候选构建和独立 Reviewer；
2. `run`：额外执行原始目标 baseline、候选原测试和预配置能力检查；
3. `repair`：对已有候选执行生成后提供的真实使用检查，并在需要时修复。

未知目标没有预配置 checks 时使用 `patch`，不应为了调用 `run` 而预先猜测 Agent 将生成的 API。一个成熟目标可以增加更严格的回归检查，但额外检查只属于该目标，不自动成为其他目标的强制要求。

隐藏 fixture 和人工 ground truth 属于正式评测工具：

- fixture 在 Reviewer 完成后才进入候选 worktree；
- ground truth 只做事后评分；
- 二者都不会进入 Agent Prompt。

因此，工程使用不要求先人工写出一份完整答案。

## 实验失败的处理规则

每次失败先分类，再决定是否修改框架。

### 通用框架错误

例如 Agent 能看到隐藏 fixture、worktree 污染原仓库、结构化输出无法审计。这类问题修改 ConsensusSeam。

### 目标项目限制

例如某个目标只有异步投递、某种运行模式没有同步错误、某个测试辅助包只支持连续节点 ID。这类问题记录在该目标报告或 evaluation 中。

### v0.1 范围之外

例如真实网络调度、跨进程持久化恢复、所有并发竞争和完整协议证明。明确记录后停止扩张，不新增全局规则。

单次实验失败是研究数据，不等于框架必须修到该实验通过。

## 已保留的工程安全措施

- Python 3.10+，不依赖 3.12 专属功能；
- Pydantic 严格 Schema；
- Agent 角色工具隔离；
- Git worktree 隔离；
- 禁止修改已有 Go 测试；
- 失败候选不会污染下一轮；
- 模型推理正文不进入审计产物；
- API 密钥不写入日志；
- 目标和控制器版本写入 `run-config.json`。

这些措施解决的是实验隔离和可追溯性，不应继续扩展成目标语义的完备 gate。

## 当前阶段

Mini Raft 用于验证完整工作流和消息控制补丁。etcd/raft 用于检查框架能否适应不同于 Mini Raft 的代码结构。

接下来的首要任务是：

1. 保持 Agent 1 六种分类和 Agent 2 单一角色稳定；
2. 用功能合同描述显式缓存、指定实例操作、所有已发现路径和正常输入边界，不强制路径数量、数字 ID 或固定方法名；
3. 通过 `USAGE.md` 接口矩阵与示例服务测试方，通过 `AUDIT.md` 保存完整英文技术分析；
4. 将额外严格检查留在具体 evaluation，并用不同结构的共识实现继续验证通用性。
