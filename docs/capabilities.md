# 七项测试控制能力总览

ConsensusSeam v0.1 只面向 Go 共识实现。能力规范约束测试方最终能做的
事情，不规定统一类型、方法名、缓存结构或节点架构。提供给 Agent 的英文
合同位于 `spec/capabilities.yaml`。

## 分类与路径

- `SUPPORTED`：边界内所有已发现的相关路径已经完整提供该能力。
- `PATCHABLE`：至少一条缺失路径可以低侵入补齐。
- `PARTIAL`：部分路径可用，但其余缺口不能安全补齐。
- `INVASIVE`：需要改变核心语义或发明目标没有定义的行为。
- `UNKNOWN`：源码证据不足。
- `NOT_APPLICABLE`：相对于当前系统边界不适用。

人工只定义系统边界，Agent 从源码发现路径。一条路径表示测试方通过一组
一致的公开输出边界、缓存所有权、输入边界和控制方式驱动系统。不同公开
节点 API、输入输出边界、所有权或同步/异步控制面通常是不同路径；消息
类型、helper、文件和到达同一控制面的内部条件分支不是不同路径。同一运行
对象上的多个 accessor 只是入口，除非所有权、边界或完成语义发生变化。
连续的发送端和接收端边界共同组成一条端到端路径，不能拆成两条；排除项、
拒绝状态和相邻原语进入证据或限制，不进入 `execution_paths`。
不同消息类型或 handler 如果共享同一 transport、缓存、输入、所有权和完成
模型，仍是一条路径。能力缺失或侵入也不能让适用路径从报告中消失。

能力是否可用必须从清单声明的测试方范围判断。项目自用测试包、同包测试、
`_test.go` 符号和内部 harness 可以提供证据与实现参考，但不能仅凭项目自身
测试能够调用就对外部测试方声称 `SUPPORTED`。技术上可以 import 的包也不
自动等于项目承诺的外部测试接口。测试辅助 facade 如果与公开原语共享相同
所有权、边界和完成语义，只是入口；如果它引入独立缓存或继续传递权，则应
与直接公开路径分别说明，不能让 facade 隐藏仍可独立使用的公开路径。
facade 围绕可独立驱动的公开运行对象拥有缓存时，两者必须作为不同路径分析
和实现，不能借 facade 的缓存把直接路径写成完整支持。
各项能力应尽量沿用同一运行路径划分：不能因为内部状态相同就合并所有权或
完成语义不同的公开对象，也不能仅因状态来自另一个 accessor/store 就新增
路径。

消息捕获和注入必须使用同一组路径名称逐条分析。不能用 A 路径的捕获和
B 路径的注入拼成完整支持。每条未覆盖路径都要说明原因，但不能为了覆盖
而修改协议核心。所有能够通过缓存、薄包装、hook 或依赖注入低侵入完成的
路径都必须实现；“当前没有 helper”正是待补缺口，不能成为只实现最方便或
项目自用测试路径的理由。

## 1. 消息捕获

目标：受控协议输出在投递前由测试可见缓存接管，后续投递只能由测试动作
触发。

测试方应能：

- 枚举缓存，查看目标原生消息内容和当前顺序；
- `Take` 一个实例并获得消息及已有路由信息；
- `Drop` 一个实例；
- `Clear` 缓存。

`Take` 属于捕获缓存操作：它移除并返回消息，但不负责协议投递。方法名并
不固定。一次性返回值、channel、投递后日志、不可控内部队列或测试方自行
创建的集合都只是原语，不是完整缓存。受控模式下捕获点必须拥有消息继续
传递权；另起消费者与协议消费者竞争读取不能构成可靠捕获。

测试方根据消息内容选择实例。实例引用可以是 record、handle、pointer、
token 或不会静默改变含义的 index。引用要么仍命中观察到的实例，要么明确
报告过期；不要求永久数字 ID。直接改写导出的 slice/map，或者一次处理全部
匹配值的批量接口，不能代替明确的单实例枚举、`Take` 和 `Drop`。

## 2. 消息注入

目标：把捕获缓存中的具体实例通过同一路径的正常协议输入边界投递，保持
消息内容和目标不变。

允许两种形式：

### 分离式注入

```text
message := Take(reference)
ProtocolInput(target, message)
```

测试方已经持有真实目标对象关系时，可以根据返回的目标原生路由信息调用
正常输入。`Take` 后消息已离开缓存；后续重试、重新入队、重复投递或丢弃
由测试方决定。

### 组合式单调用注入

```text
Inject(reference)
```

facade 在一次调用中定位实例、绑定或校验目标、执行正常输入并更新缓存。
“单调用”不表示事务原子性。接口报告必须说明成功、同步失败和未确认异步
投递分别如何影响缓存。

如果目标采用请求—响应、response channel 或 future，捕获、移除、超时和
注入还必须保留并说明原有完成机制，不能让发送方或 future 静默失联。
捕获的请求必须进入正常请求处理入口；直接构造或完成响应不能代替请求
注入。只有缓存实例本身是响应时，才通过响应入口注入该实例。

两种形式都是完整注入，不要求同一系统同时提供两种。普通输入函数只有与
同一路径的捕获缓存建立明确关系后才算完整注入。
只有目标自身建立并校验的 ID、索引或注册关系才能证明真实目标绑定；单纯
依赖命名或算术换算不够，目标无法解析时还要明确失败和缓存效果。

## 3. 时间控制

测试方能够通过显式 Tick 或可注入 Clock 确定性推进协议时间。已有接口可
直接使用时不重复包装；不得新增直接制造选举或超时结果的捷径。新增控制
值必须遵守目标合法范围。只有能影响协议状态、消息或持久化的时间才属于
该能力；调用方 deadline、metrics、日志和纯展示时间只作为限制记录。
没有 Tick、真实时间调用分散或需要修改多个文件，本身都不等于侵入式。
如果注入 Clock/Timer 后能保持生产默认、timer 顺序和协议转换条件，应判为
`PATCHABLE`；只有必须重设计调度、事件顺序或协议语义时才是 `INVASIVE`。
每条声称支持的路径都必须可靠接受并执行测试方请求的时间推进；可能静默
丢弃、合并或无限延后 Tick/Timer 事件的异步入口，不能借另一条精确路径证明
自身完整支持。

## 4. 随机性控制

相同初始状态、控制参数和测试调度应重现每个实例相同的协议随机选择序列，
并让测试方在安排依赖动作前知道每次实际选择值。随机值可以在每次决策或
重置时变化，可复现不等于永远固定。可以复用配置、显式选择、seed、注入
随机源、hook 或测试构造器，但不能替换随机算法；接口还要保持生产默认并
校验合法值域。共享 seeded 随机源在相同调度下能够稳定分配选择时可以满足
要求，只有相同调度仍可能让选择漂移到不同实例或决策时才不完整。

不影响协议决策的随机地址、setup ID 和日志值不属于随机性路径。

## 5. 生命周期控制

测试方能够 crash 指定逻辑节点，并通过目标正常恢复路径 restart。最小状态
模型是“持久状态 D + 易失状态 V + 测试缓存中的在途消息 M”：crash 停止协议
活动、丢弃旧的 V，只保留目标在 crash 点已经持久化的 D；restart 从 D 创建
新的运行实例。已有操作可以直接组合时不要求 convenience wrapper，但继续
使用同一内存对象的 pause/resume、优雅停止、网络断连、丢包或分区都不能
证明 crash/restart。

Seam 不发明持久化语义，不改变目标既有的“持久化后才允许发送”等顺序，
也不自动实现恢复后的日志追赶。已经进入测试缓存的 M 仍由测试方控制；测试
方恢复投递并观察节点是否正确追赶。目标没有持久状态或正常恢复入口时，应
如实报告限制或侵入性，而不是保存整份易失内存来伪装恢复。

## 6. 状态观察

暴露测试所需的最小目标原生节点或全局状态。已有 Status 足够时直接复用，
状态分散时可以增加只读 accessor。返回结果不能通过共享可变数据修改内部
状态；Go 结构体按值复制后仍要检查嵌套 slice、map、pointer、interface 和
可消费流。文档要求调用者“不要修改”不能把共享底层存储变成安全快照。
每条运行路径只需要一个安全的最小观察接口，不把所有相关
accessor 或测试方持有的 store 都纳入正向声明。v0.1 不设计统一状态 Schema
或正确性 oracle。

## 7. 外部输入

发现已有 proposal、read request、transaction、成员变更或其他应用工作
入口，并生成清晰清单。它只做发现，不创建业务 API。点对点协议 ingress、
Tick、定时器、内部 callback，以及诊断、barrier、snapshot/restore、
bootstrap、领导权转移、生命周期和维护操作不属于外部输入，除非目标明确
将其定义为应用工作负载。
成员变更请求的提交可以是外部输入；应用已经提交的成员变更结果只是消费
协议输出，不是新的外部工作入口。

## 通用实现与审查原则

- 区分底层原语和测试方可直接使用的完整接口；
- 复用已有能力，缺失时才包装、暴露或最小实现；
- 优先向声明的外部测试方交付可正常 import 的接口；项目自用测试包主要
  用作实现参考和回归验证，只有它是明确的外部测试 API 或侵入最低的完整
  方案时才作为主要交付面；
- 如实记录外部、公开测试辅助、同包测试和内部 harness 的调用范围；
- `entrypoints` 只写未修改源码中已存在且声明测试方可调用的接口，候选设计
  只进入 `suggested_changes`；
- 返回快照不能泄漏可变别名；
- 只生成七项能力所需的接口机制，不把场景语言、调度/变异策略、故障模型、
  断言或正确性 oracle 写入目标；
- 成功、失败和控制状态变化必须与报告一致；
- 使用示例必须使用正确 receiver 和声明范围可见的真实符号；无法确认时应
  省略，不能使用省略号、伪造 helper、未导出字段或未使用变量；允许通过
  `// Requires:` 声明预先存在变量及其 Go 类型；
- Agent 2 只添加验证新增行为所需的最少测试，不扩写重复或穷举测试。

每次运行通过 `capability-report.json`、`interface-report.json`、`USAGE.md`
和 `AUDIT.md` 分别记录修改前事实、生成接口、使用方式和独立审查结论。
`patch` 已经能够产出候选；`repair` 只是生成后的可选质量增强流程。
