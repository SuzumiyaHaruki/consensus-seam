# 七项测试控制能力总览

本文档面向 ConsensusSeam 使用者，说明 v0.1 分析的七项能力、分类方式和每次实验的总结产物。提供给 Agent 的英文合同位于 `spec/capabilities.yaml`。

## 能力分类

- `SUPPORTED`：系统边界内所有已发现的相关路径已经提供该能力。
- `PATCHABLE`：至少一条当前缺失路径可以通过低侵入修改补充；其他不可补充路径仍需报告。
- `PARTIAL`：部分路径已有能力，但剩余缺口都不能在 v0.1 中安全补充。
- `INVASIVE`：实现需要改变核心语义或发明目标没有定义的行为。
- `UNKNOWN`：源码证据不足。
- `NOT_APPLICABLE`：相对于当前系统边界不适用。

人工只负责定义系统边界，不负责列出目标内部实现路径。Analyzer 应发现所有输入、输出或控制边界实质不同的公开路径；Transformer 应尽可能覆盖所有低侵入可实现路径。

## 原语、测试支持与状态

“系统已经有底层操作”不等于“系统已经有测试接口”。每项能力都要记录：

- `existing_test_interface_complete`：现有接口是否已经完整满足测试能力；
- `test_support_reason`：为什么现有原语已经足够或仍有缺口；
- `suggested_changes`：可以低侵入采用的候选改造。

`SUPPORTED` 表示无需新增代码即可满足能力合同。现有原语足够作为基础、但仍需包装、hook、依赖注入、配置、accessor 或测试 harness 扩展时应为 `PATCHABLE`。Analyzer 给出建议，Transformer 根据实际代码选择实现方式。

## 1. 消息捕获

目标：受控路径的协议输出在继续传递前进入测试可见的显式缓存，并由测试方决定何时以及如何处理。目标可能没有、只有一条或具有多条重要路径，具体数量和形态必须由 Agent 从源码发现，不能写成全局前提。

基本接口信息包括：

- 查看缓存消息内容和当前顺序；
- 阻止缓存消息自动继续原路径；
- 准确操作一个由测试方指定的缓存实例；
- 移除或清空缓存消息。

缓存必须是目标提供或由 Agent 补充的测试控制状态：捕获实例在显式消费或删除前持续保留，并能跨多次捕获操作查看。一次性返回值、channel 交付、不可由声明消费者控制的内部队列，或者“测试方可以自行新建切片保存”都只能证明消息可观察，不能证明目标已经提供缓存。

不同路径可能在协议核心、应用传输层或测试环境中暴露消息，Agent 不能假定所有目标都有特定传输抽象，也不能用一条已有完整测试环境的路径替代其他仅暴露输出原语的路径。`SUPPORTED` 要求每条重要路径都已经具有声明消费者可调用的缓存控制面。

目标已有切片、队列或测试缓存可以作为唯一权威存储，由 Agent 包装或扩展其控制操作，不应复制成容易失去同步的平行缓存。但公开可变切片加批量过滤不等于精确实例控制：如果测试方仍要手工切片，或平行元数据无法感知外部修改，合同仍不完整。

“如何选择”和“如何引用”必须分开。测试方根据目标原生消息内容选择；缓存枚举同时返回与具体实例绑定的记录、opaque handle、token、指针或可选控制 ID，后续操作使用这个引用。裸下标在删除前序消息、并发捕获、排序或外部修改后可能指向另一条消息，因此只有在观察与操作原子化、带版本或明确保证无中间变更时才成立。两个内容完全相同的消息也必须可以分别控制。

## 2. 消息注入

目标：测试代码指定一个缓存消息实例，并通过真实目标的正常协议输入入口进行投递。

选择哪条消息、何时投递以及是否重试属于测试策略。ConsensusSeam 提供与消息捕获共享同一权威缓存的控制面：可以采用缓存 `Take` 后进入目标绑定的正常输入操作，也可以提供组合式 `Inject`，但不能只列出一个接受任意消息的输入函数。控制面应解析缓存中记录的目标到真实对象；如果目标架构必须由调用方传入对象，也必须校验它与缓存实例匹配，不能把对应关系完全交给测试方猜测。Agent 还要说明缓存删除、同步错误和未确认异步发送的真实语义。

消息注入通常复用消息缓存与目标已有的正常协议入口，不要求所有目标采用相同的组合方法。只有某条路径同时具备缓存、具体实例操作和与真实输入边界的明确关系时，该路径才算完整支持注入。

消息捕获和注入在报告中仍是两项能力，但实现时属于同一个消息控制面。两项同时需要补充时，Transformer 必须联合设计，Reviewer 必须检查它们是否共享同一权威缓存以及一致的消费、失败语义。

## 3. 时间控制

目标：测试代码能够确定性推进协议观察到的时间。

v0.1 接受显式 Tick 或可注入 Clock，不增加直接制造选举或超时结果的捷径。

单节点 Tick 已经可以直接供测试使用时不需要改造；如果需要同时推进多个节点、处理异步完成或统一多个时间入口，可以增加协调包装或测试 harness 方法。

## 4. 随机性控制

目标：协议相关随机性可以固定或注入，使相同初始状态和种子产生可重复选择。

接口应保留目标原有随机算法和默认生产行为。

改造可以表现为 Config 选项、依赖注入、可设置随机源或测试构造器，不应新增另一套随机算法。

## 5. 生命周期控制

目标：把目标已有的“使节点不可用”和“恢复可用”入口暴露给测试。

第一版允许 pause/resume、graceful stop/restart、从已有 Storage 重建或外部进程控制，但必须如实说明实际机制。Pause 可以模拟节点暂时不可用，不能被描述成完整生产 crash。

对于由调用方直接驱动的同步对象，停止调度并在之后恢复调用也可以满足 availability-only 的最低要求；如果目标已经公开了重建所需的状态和构造入口，手工组合重建同样成立。第一版不要求每个测试环境都再增加专门的 pause/restart 命令，不能仅因缺少 convenience wrapper 就标为 `PATCHABLE`。

只有目标明确提供持久状态所有权和恢复边界时，Agent 才能声明 crash/recovery fidelity；可用性模拟不涉及持久化时，相关义务应标为 `NOT_APPLICABLE`，不能自行决定哪些状态在崩溃后保留。

## 6. 状态观察

目标：暴露后续测试所需的最小节点或全局状态。

字段可以保持协议和实现特有，例如角色、任期、提交位置、应用位置或日志范围；v0.1 不设计统一状态 Schema。

如果状态分散在多个已有入口中，可以增加只读 accessor 或聚合包装；已有 Status 已经足够时不重复实现。

## 7. 外部输入

目标：发现系统已有的应用工作入口，例如 proposal、read request、transaction 或成员变更。

它只做发现，不创建新的业务 API。点对点协议消息、Tick、定时器和内部回调不属于外部输入。

## 多路径记录

每项能力报告可以包含：

- `execution_paths`：Analyzer 发现的实质不同路径；
- `entrypoints`：目标已有入口；
- `covered_paths`：Agent 2 已实现或补充的路径；
- `uncovered_paths`：仍未覆盖的路径及原因；
- `limitations`：系统边界或 v0.1 范围限制。

未覆盖路径不是自动失败，但静默遗漏路径属于分析或实现问题。

## 每次实验的能力总结

每次运行生成：

- `capability-report.json`：机器可读的七项能力分析；
- `interface-report.json`：机器可读的新增接口说明；
- `USAGE.md`：面向测试方的简洁接口矩阵、调用入口、示例和剩余限制；
- `AUDIT.md`：修改前分析、路径证据、实现方式与 Reviewer 结论的完整审计说明。

analyze-only 运行没有 `interface-report.json`，但仍会生成 `USAGE.md`，总结目标已有能力和待补充能力。

`patch` 完成时已经产出可用的接口候选，不要求继续执行 `repair`。如果使用者希望进一步提高候选质量，可以基于真实 API 编写测试，并通过可选的 `repair` 把失败反馈给 Agent 2。这样 capability checks 不需要提前猜测接口形状，同时保留独立的自动修复能力。

首次生成不依赖人工后置测试来完成基本质量闭环。Agent 3 必须检查以下通用接口性质，并把违反合同的问题自动路由回前两个 Agent：

- 入口对报告声明的使用者范围确实可调用；
- 返回快照不会通过切片、指针或嵌套对象修改内部状态；
- 新增 ID、索引或元数据与目标已有修改入口保持一致；
- 注入成功、消息消费和真实输入边界的接受语义一致；
- 时间、随机性等配置值遵守或显式验证目标已有合法域。

这些要求描述行为，不规定目标必须使用某种队列、transport、节点容器或复制函数。
